## Headline finding

suggestion at all** — no `help`, no `note`. It reports the conflict and stops.

So an agent that follows the compiler faithfully gets nothing to act on in most
borrow conflicts, and gets told to clone in the one place it does get advice. Clone
is the move that always compiles, so it becomes the default. That is the mechanism
behind clone-spam — a guidance vacuum, not laziness.

## `e0502-cache-lookup.rs`

**Scenario.** Read from a map, then insert into it while the read is still live.

**Compiler says** — `E0502`: cannot borrow `*cache` as mutable because it is also borrowed as immutable

_rustc offered no `help`/`note` suggestion for this one._

**What agents reach for.** Clone the looked-up value (or the whole entry) so the immutable borrow ends early.

**Why that is wrong.** Allocates on every lookup on the hot path, and if the agent clones the map instead of the value, later reads silently observe a stale copy.

**Correct fix.** End the borrow before the mutation — bind only what you need (a bool, a length, an owned key) inside a tight scope, or use the entry API.

**Does clippy catch it?** No. The original is still used afterwards, so the clone is not redundant in clippy's sense.

## `e0382-use-after-move.rs`

**Scenario.** A value is moved into a function, then used again by the caller.

**Compiler says** — `E0382`: borrow of moved value: `s`

| rank | level | suggestion |
|---|---|---|
| 1 | `note` | consider changing this parameter type in function `consume` to borrow instead if owning the value isn't necessary |
| 2 | `help` | consider cloning the value if the performance cost is acceptable |

**What agents reach for.** Pass s.clone() to the function.

**Why that is wrong.** Copies the whole value on every call when the callee only needed to read it.

**Correct fix.** Change the parameter to &str / &String so nothing moves.

**Does clippy catch it?** No. rustc itself suggests the clone as a `help` — see EVIDENCE.md.

## `e0499-two-mut-borrows.rs`

**Scenario.** Two mutable borrows of the same collection are live at once.

**Compiler says** — `E0499`: cannot borrow `v` as mutable more than once at a time

_rustc offered no `help`/`note` suggestion for this one._

**What agents reach for.** Clone the collection so each borrow gets its own copy.

**Why that is wrong.** The two halves of the code now mutate different objects; writes through one are invisible to the other. This compiles and is silently wrong.

**Correct fix.** Sequence the borrows so only one is live at a time, or use split_at_mut / indices.

**Does clippy catch it?** No. Both clones are used, so redundant_clone stays silent. This is the dangerous class.

## `e0506-assign-to-borrowed.rs`

**Scenario.** A field is assigned while a reference into it is still live.

**Compiler says** — `E0506`: cannot assign to `cfg.retries` because it is borrowed

_rustc offered no `help`/`note` suggestion for this one._

**What agents reach for.** Copy the field into a local before assigning.

**Why that is wrong.** For Copy types this is fine; for owned data the agent tends to clone the whole struct, and the reader then observes the pre-mutation snapshot.

**Correct fix.** Read the value out (it is Copy here) or shorten the reference's lifetime to before the assignment.

**Does clippy catch it?** No. Semantic, not a waste lint.

## `e0515-return-local-ref.rs`

**Scenario.** A function returns a reference into a local.

**Compiler says** — `E0515`: cannot return reference to local variable `owned`

_rustc offered no `help`/`note` suggestion for this one._

**What agents reach for.** Leak the string, or return a clone with a 'static bound via Box::leak.

**Why that is wrong.** Box::leak turns a per-call allocation into a permanent one — a real memory leak that compiles and passes tests.

**Correct fix.** Return the owned String, or take a buffer from the caller.

**Does clippy catch it?** No. Box::leak is legitimate in other contexts, so no lint fires.

## `e0597-borrow-outlives.rs`

**Scenario.** A reference outlives the scope of the value it points into.

**Compiler says** — `E0597`: `inner` does not live long enough

_rustc offered no `help`/`note` suggestion for this one._

**What agents reach for.** Hoist the inner value out, or clone it into the outer binding.

**Why that is wrong.** Cloning here is often correct — but agents also reach for Rc/RefCell, moving a compile-time error to a runtime panic.

**Correct fix.** Restructure so the value outlives the reference; only reach for Rc/RefCell when sharing is genuinely required.

**Does clippy catch it?** No. RefCell misuse surfaces as a runtime BorrowMutError, not a lint.
